# Погода Дальнего Востока

MVP сравнивает независимые прогнозы ECMWF IFS, NOAA GFS и DWD ICON в контрольных
точках всех 11 субъектов Дальневосточного федерального округа. Интерфейс
показывает температуру, осадки, ветер, согласованность моделей и объяснимые
аналитические карточки на сегодня, 3 и 7 дней.

Список субъектов ограничен официальным перечнем
[полпредства Президента РФ в ДФО](https://dfo.gov.ru/district/):

- Амурская область
- Еврейская автономная область
- Забайкальский край
- Камчатский край
- Магаданская область
- Приморский край
- Республика Бурятия
- Республика Саха (Якутия)
- Сахалинская область
- Хабаровский край
- Чукотский автономный округ

## Быстрый запуск

С Docker:

```bash
cp .env.example .env
docker compose up --build
```

- интерфейс: http://localhost:3000
- API: http://localhost:8000
- Swagger: http://localhost:8000/docs

Без Docker:

```bash
cd apps/api
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
uvicorn app.main:app --reload --port 8000
```

В другом окне:

```bash
cd apps/web
npm install
npm run dev
```

По умолчанию используется детерминированный `DATA_MODE=mock`; интернет не нужен.
Для Open‑Meteo задайте `DATA_MODE=live` и перезапустите backend.

## Выбор региона и URL

Пикер получает алфавитный список через `GET /api/regions`. При смене региона
очищаются старые маркеры, выбирается административный центр, карта получает
индивидуальные center/zoom, а прогноз загружается лениво только для нового
региона. Горизонт и раздел сохраняются.

URL хранит `region`, `horizon`, `date`, `section`, `view` и `point`, например:

```text
/?region=khabarovsk-krai&horizon=7d&date=2026-08-03&section=wind&view=period&point=komsomolsk-on-amur
```

Без `region` временно выбирается `amur-oblast`. Неизвестный id обрабатывается без
падения: интерфейс показывает уведомление и возвращается к региону по умолчанию.
Кнопки браузера назад и вперёд восстанавливают полное состояние.

## Данные регионов

`data/regions/regions.json` — единый registry. Каждый регион имеет отдельный файл
точек `data/regions/{region_id}.json`. Количество точек различается, потому что
учитываются размеры и география территории; всего в текущем наборе 237 точек.
Крупнейшие населённые пункты дополнены северными, южными, западными и восточными
точками.

Координаты, принадлежность административному коду и timezone взяты из ежедневной
выгрузки GeoNames, а у каждой точки сохранены `source_id`, URL и дата проверки.
Наборы отмечены `partially_verified`: координаты опубликованы и машинно
проверяются, но полнота климатического покрытия требует дальнейшей экспертной
проверки. Подробнее: [data/regions/SOURCES.md](data/regions/SOURCES.md).

GeoJSON не аппроксимируется. Пока проверенные файлы границ не подключены, карта
центрируется по registry и показывает только точки. Это не мешает прогнозу.

## Часовые пояса

Исходные timestamps хранятся в UTC. Каждый `ForecastPoint` содержит собственный
IANA timezone, по которому вычисляются `forecast_time_local` и `local_date`.
Горизонт интерфейса формируется по `primary_timezone` административного центра.
Для Якутии, где выбранные точки охватывают несколько timezone, интерфейс явно
показывает пояс общей даты и местный пояс точки.

## API и lazy loading

Региональные endpoints:

```text
GET /api/regions
GET /api/regions/{region_id}
GET /api/regions/{region_id}/points
```

Погодные endpoints принимают `region_id`:

```text
GET /api/forecast
GET /api/forecast/{point_id}
GET /api/summary
GET /api/insights
POST /api/refresh
```

Backend запрашивает единый семидневный набор выбранного региона. Переключение
горизонта, раздела и даты фильтрует свежий кэш и не вызывает Open‑Meteo повторно.
Ключ хранения включает `region_id`; ручное обновление затрагивает только выбранный
регион. Live-запросы используют настраиваемые `OPEN_METEO_BATCH_SIZE` и
`OPEN_METEO_MAX_CONCURRENCY`.

Ряды ECMWF, GFS и ICON нормализуются отдельно. Суточные показатели сначала
вычисляются внутри одной модели и локального дня точки, и только после этого
поступают в статистический слой. Пропуски остаются `null`, ложный консенсус по
одной модели не создаётся.

Для периодных осадков приложение сначала вычисляет суточную сумму каждой модели
в каждой точке, затем строит взвешенное среднее по точкам региона и только после
этого суммирует дни. Итоги ECMWF, GFS и ICON накапливаются независимо; консенсус
рассчитывается после накопления. Осадки разных контрольных точек не складываются
между собой.

## Как добавить новый регион

1. Добавить стабильный id и метаданные в `data/regions/regions.json`.
2. Создать `data/regions/{region_id}.json`.
3. Проверить координаты и принадлежность каждой точки опубликованным источником.
4. Указать IANA timezone каждой точки и `primary_timezone` региона.
5. При наличии добавить лицензированный GeoJSON в `data/geo/regions`.
6. Дополнить `data/regions/SOURCES.md`.
7. Добавить mock-сценарий или fixture.
8. Запустить validation tests и полный набор проверок.

Текущий MVP намеренно не добавляет регионы вне ДФО и не сравнивает регионы между
собой.
